1. Docker Engine API exposed without TLS

10.0.0.20 (lab-app.internal)
Port
2375/tcp
Confidence
Confirmed: nmap identified the service by probing it
Rule
RR-API-DOCKER

Evidence

docker: Docker 24.0.7

Description

The Docker daemon API is reachable over plain TCP. The API has no authentication of its own, and anyone who can reach it can start privileged containers, which is equivalent to root access on the host.

Recommendation

Stop exposing the daemon over TCP: use the local Unix socket, or SSH. If remote TCP access is required, use TLS with client certificate verification (--tlsverify) and restrict the port to trusted hosts.

References

  • https://docs.docker.com/engine/security/protect-access/

Evidence

vnc: VNC (protocol 3.8)

Description

VNC often relies on a single shared password, and classic VNC authentication uses only the first 8 characters of it. Many deployments send the session unencrypted, and some allow access with no password at all.

Recommendation

Do not expose VNC directly. Tunnel it over SSH or a VPN, require strong authentication, and prefer a VNC server that supports encryption. If remote access is required, allow it only from trusted management networks through a firewall or VPN rather than exposing it broadly.

Description

The banner reports Apache httpd 2.4.49 or 2.4.50. 2.4.49 is affected by CVE-2021-41773, and both versions by CVE-2021-42013 (an incomplete fix for the first). Depending on configuration, these allow reading files outside the document root and, with CGI enabled, remote code execution. The Apache project reports CVE-2021-41773 was exploited in the wild.
